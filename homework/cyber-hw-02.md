# Findings Analysis & Remediation
Target 1: target 1 has 4 warnings, 0 info, and 0 critical. Of the 4 warnings 3 of them are in the filesystem. Those three can be seen in these particular links: /usr/libexec/utempter/utempter (this is an unexpected ID for either a group or single user), /usr/local/bin/legacy-monitor (unexpected set user ID), and  /usr/bin/write (unexpected set group ID). Then the final warning is found in the accounts namely in the user ta which had the sudo access of NOPASSWORD:ALL. This account warning I believe is the most urgent finding because you can execute root commands with no passwords required which is obviously extremely dangerous for your whole system to be altered by attackers as well as accidental damage from uninformed employees that go beyond their privileges without meaning to. For remedies I would remove this user system entirely by typing this command into the terminal -sudo rm /etc/sudoers.d/90-ta-nopasswd I would then check all my administration rules through sudo visudo -c to see if it worked. For the other filename warnings I would want to strip the general SUID permissions through the command sudo chmod u-s /usr/local/bin/legacy-monitor. 

Target 2: target 2 has 7 warnings and 0 criticals or info. Similar to target 1 this target has 5 warnings within the filesystem with /opt/vendor-agent/bin/collector, /usr/libexec/utempter/utempter, and /usr/bin/write having SUID/SGID concerns but the file /etc/motd.d/welcome.txt is a certain file that any user has permission to modify or delete sometimes called a world-writable. And the last warning file is /home/former-employee/scripts/backup.sh which has either user or group IDs that do not go with any existing accounts also known as an unknown UID/GID. The 2 remaining warnings exist within the accounts and we have the ta user with NOPASSWD:ALL sudo access. We also have the service account svc-legacy that has elevated administrative privileges even though it is currently inactive and possibly no longer needed. As with the first target I believe that the ta user is the most urging warning here for all the same reasons. For the NOPASSWD I would use the sudo rm /etc/sudoers.d/90-ta-nopasswd and sudo visudo -c again. For the SUID/SGID concerns I will strip the permissions through sudo chmod g-s /opt/vendor-agent/bin/collector. For the word-writtable I will remove its access through sudo chmod 644 /etc/motd.d/welcome.txt. For the former employee folder I will assign its ownership to root through sudo chown root:root /home/former-employee/scripts/backup.sh. And finally I will simply remove svc-legacy account through sudo gpasswd -d svc-legacy wheel and then sudo usermod -L -s /sbin/nologin svc-legacy. 

Target 3: Target 3 has 5 warnings, 2 criticals, and 0 info. The critical concerns are first /etc/shadow which is a folder holding sensitive information. It is showing to be in mode 644 instead of 000 which means it is in read mode for any user that comes across it so anyone can read the sensitive data that is on it. The second critical concern is that SSH has direct root login which simply means that any remote shell is capable of direct root access to the whole system. The warnings are all things we’ve seen before. /usr/bin/write, /usr/local/bin/.hidden_shell, and /usr/libexec/utempter/utempter are all unexpected SUID/SGID. /etc/cron.d is another word-writable. And just like the last 2 targets we have the ta user with NOPASSWD:ALL sudo access. By far the most urgent concern here is the /etc/shadow since this contains all the passwords for the system. The fix is quite simple. I would change the permissions through sudo chmod 000 /etc/shadow. For the second critical concern I would set the PermitRootLogin to no instead of yes through sudo sed -i 's/^PermitRootLogin yes/PermitRootLogin no/' /etc/ssh/sshd_config and then apply the changes by reloading the ssh daemon through sudo systemctl reload sshd. For the word-writable I would type sudo chmod 755 /etc/cron.d. For the passwordless user I would use sudo rm /etc/sudoers.d/90-ta-nopasswd and sudo visudo -c again. I would delete hidden_shell folder do to deep suspicion through sudo rm /usr/local/bin/.hidden_shell. But then I would just try to compare the other warned files to safe ones before determining if they should be messed with.

Ranking: Conveniently the ranking of these targets from the highest risk to lowest goes down in reverse numerical order with target 3 being highest risk, target 2 being the second highest risk, and target 1 having the lowest risk overall. Target 3 is the only target with critical concerns not just warning and both of those concerns could lead to the complete destruction of the system. The second target has 3 more warnings then target 1 has a more diverse range of issues that could be exploited like word-writable files and stale privileged accounts. And finally target 1 has only 4 warnings and no criticals and all the issues in target 1 can be found in the other targets as well.

1 hour question: I would pick target 3 because all the other targets have warnings whereas this target has critical issues. If /etc/shadow and direct root SSH access aren’t changed then there is nothing that would stop an attacker from having full access to the system.

# Reflection Write-up
1.  I think for 200 servers I wouldn’t want to use the same SUID whitelist for every server. I think it would be good to have different types of whitelists since some servers are doing different things (web, database, build as stated). I would create different whitelists for each type of server while also keeping all of them in one central system. Then each server could be checked against the whitelists for their specific role. I would also probably need a process that approves new programs so those programs don’t create any false alarms in the system.
2.  For this script I might have trouble detecting a Process Injection (MITRE ATT&CK T1055) where an attacker would place malicious code into a running process. The reason the attacker would be successful is because the script really only checks  files, user accounts, network connections, SSH settings, and scheduled tasks but doesn’t really account for what happens inside process memory. If we added an EDR (Endpoint Detection and Response) then I think that would be properly accounted for.
3.  The biggest issue here is the filesystem category because it would make a lot of false positives on 200 servers. Because people would be making so many different and seemingly strange programs the script would constantly be reporting threats from actions that were actually normal. One way I could limit this is by being particular with when things are flagged in the system such as only reporting a word-writable file that is in a sensitive location (like /etc or /usr) instead of every word-writable. And as far as what I would put as highest priority I believe I would choose any cron threats mainly because cron gives a user complete root control which would be catastrophic to the system and would end up being a critical find not a warning.
